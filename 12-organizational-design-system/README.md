# Organizational Design System

### A practical system for designing an organization around strategy, accountability, decision-making, capability, and execution.

An organization chart shows reporting relationships.

It does not tell leadership whether the organization can execute the strategy.

Organizational design should answer:

1. What work must the organization perform?
2. What capabilities does the strategy require?
3. Where should accountability sit?
4. Which decisions belong at which level?
5. How should work be grouped?
6. Where are critical interfaces?
7. How many management layers are necessary?
8. What span of control is appropriate?
9. Where does complexity create friction?
10. What leadership capacity is required?
11. What should be centralized, decentralized, or shared?
12. What must change for the organization to perform better?

> **Design the organization around the work and outcomes required, not around the people currently occupying the boxes.**

---

# The Organizational Design Logic

The operating logic is:

**Strategy → Required Outcomes → Work → Capabilities → Accountability → Decisions → Structure → Interfaces → Roles → Talent → Management System → Performance**

Structure is one component.

The objective is organizational effectiveness.

A strong design should improve:

- Accountability
- Decision speed
- Customer responsiveness
- Execution
- Productivity
- Collaboration
- Leadership leverage
- Cost
- Scalability
- Capability
- Adaptability

Do not reorganize because the chart looks complicated.

Redesign when the operating model prevents the organization from delivering what the strategy requires.

**What does the strategy require the organization to be capable of doing?**

# 02. Define the Design Criteria

Establish the principles against which alternative designs will be evaluated.

Example:

| Design Criterion | Why It Matters | Priority |
|---|---|---|
| Customer proximity | Faster market response | High |
| P&L accountability | Clear economic ownership | High |
| Decision speed | Reduce execution delays | High |
| Scale efficiency | Avoid duplicated capability | Medium |
| Local autonomy | Adapt to market conditions | High |
| Functional excellence | Maintain specialist capability | Medium |

Typical criteria include:

- Customer proximity
- Market responsiveness
- Accountability
- Decision speed
- Cost efficiency
- Scalability
- Functional excellence
- Innovation
- Risk control
- Local autonomy
- Global consistency
- Leadership leverage

Do not evaluate organizational designs without explicit criteria.

Otherwise decisions become preference-driven.

**Where does ownership become unclear?**

**Where are handoffs failing?**

# 06. Identify Organizational Friction

Look for recurring symptoms.

Examples:

- Decisions repeatedly escalate
- Multiple people believe they own the same outcome
- Nobody owns a critical outcome
- Meetings substitute for decision rights
- Functions optimize against each other
- Customers navigate internal complexity
- Regional teams wait excessively for headquarters
- Headquarters lacks market visibility
- Senior leaders operate too deep in execution
- Managers have insufficient authority
- Too many approval layers exist
- Roles have overlapping mandates
- Critical capabilities sit too far from the work
- Organizational cost grows faster than output

Use:

| Friction | Evidence | Business Impact | Root Cause | Required Change |
|---|---|---|---|---|
| | | | | |
| | | | | |

Do not redesign around anecdotal frustration.

Find recurring operating patterns.

# 09. Determine the Primary Organizational Axis

Most organizations require a dominant organizing logic.

Possible axes include:

### Function

Examples:

Sales, Marketing, Operations, Finance, Product.

Useful when functional expertise and scale matter most.

### Geography

Examples:

Americas, EMEA, APAC.

Useful when markets require significant local adaptation or accountability.

### Customer

Examples:

Enterprise, SMB, Public Sector.

Useful when customer needs differ materially.

### Product

Useful when products require distinct capabilities, economics, or strategies.

### Business Unit

Useful when businesses have distinct P&Ls, markets, or operating models.

### Matrix

Useful when two dimensions are genuinely important.

Also capable of creating substantial complexity.

Define:

| Axis | Strategic Benefit | Cost / Complexity | Fit |
|---|---|---|---|
| Function | | | |
| Geography | | | |
| Customer | | | |
| Product | | | |
| Business Unit | | | |

Choose the axis that best supports the strategy.

Do not create a matrix simply to avoid making a choice.

# 14. Design Roles Around Outcomes

A role should exist because the organization requires an outcome.

For each critical role define:

| Role | Purpose | Outcomes Owned | Decisions Owned | KPIs | Critical Interfaces |
|---|---|---|---|---|---|
| | | | | | |
| | | | | | |

Avoid job descriptions dominated by activity lists.

Senior roles should be defined primarily through:

- Outcomes
- Accountability
- Authority
- Scope
- Interfaces
- Capability requirements

The role should remain understandable even if the person changes.

# 15. Review Management Layers

Every management layer should create value.

Map:

**CEO → Executive → VP → Director → Manager → Frontline**

For each layer ask:

- What decisions occur here?
- What information is added?
- What coordination occurs?
- What capability is developed?
- What risk is managed?
- What would happen if this layer disappeared?

Use:

| Layer | Purpose | Value Added | Decision Rights | Required? |
|---|---|---|---|---|
| | | | | |

Warning signs include:

- Managers managing only one or two managers
- Information repeatedly repackaged upward
- Decisions moving through multiple approvals
- Roles existing primarily to coordinate other coordinators
- Senior leaders operating at frontline level

Do not remove layers merely to make the organization flatter.

Remove layers that do not create sufficient management value.

---

# 16. Review Span of Control

There is no universal correct span.

The appropriate span depends on:

- Work complexity
- Role similarity
- Employee capability
- Geographic dispersion
- Process maturity
- Management burden
- Decision complexity
- Degree of standardization

Use:

| Manager | Direct Reports | Work Complexity | Team Maturity | Management Load | Assessment |
|---|---:|---|---|---|---|
| | | | | | |

Potential warning signs:

### Span Too Narrow

- Excessive management cost
- Micromanagement
- Too many layers
- Slow information flow

### Span Too Wide

- Weak coaching
- Poor oversight
- Slow decisions
- Limited leadership attention
- Escalation failures

Optimize span for the work.

Not for an arbitrary benchmark.

---

# 17. Review Leadership Scope

For each senior leader assess:

| Leader / Role | Scope | Outcomes | Decisions | Complexity | Capacity Risk |
|---|---|---|---|---|---|
| | | | | | |

Consider:

- Revenue responsibility
- P&L
- Headcount
- Geography
- Number of functions
- Strategic priorities
- Transformation load
- Customer complexity
- Decision volume

A role can be structurally logical and still operationally impossible.

Design for realistic leadership capacity.

---

# 18. Separate Structural Problems From Leadership Problems

Do not reorganize to solve every leadership issue.

Ask:

**Would this structure work with the right leader?**

If yes, the problem may be leadership capability.

Then ask:

**Would an excellent leader still struggle in this structure?**

If yes, the problem may be structural.

Use:

| Problem | Structural? | Leadership? | Process? | Capability? | Evidence |
|---|---|---|---|---|---|
| | | | | | |

Do not move boxes when the real issue is capability.

Do not replace leaders when the operating model makes success unlikely.

# 19. Assess Role-Capability Fit

Once the future roles are defined, assess people against the roles.

Do not design roles around incumbents.

Use:

| Future Role | Required Capability | Current Leader | Fit | Gap | Decision |
|---|---|---|---|---|---|
| | | | Strong / Partial / Weak | | |

Possible decisions:

- Retain
- Expand
- Develop
- Redefine
- Recruit
- Succession plan

Separate:

**The role the organization needs**

from:

**The person currently in the role.**

This distinction protects organizational design quality.

- Hiring decision
- Product prioritization
- Marketing investment
- Market-entry decision
- Operational failure
- Capital request

Ask:

**Who sees the issue?**

**Who owns it?**

**Who decides?**

**Who contributes?**

**How quickly can the decision occur?**

**Where could it become blocked?**

Use:

| Scenario | Owner | Decision Maker | Contributors | Expected Speed | Friction |
|---|---|---|---|---|---|
| | | | | | |

A design that looks clean but fails real decision scenarios is not ready.

# 25. Define the Transition Plan

A good future-state design can still fail during implementation.

Sequence the transition.

| Change | Current State | Future State | Owner | Effective Date | Dependency |
|---|---|---|---|---|---|
| | | | | | |

Typical sequence:

### Phase 1. Clarify

- Future model
- Accountabilities
- Decision rights
- Leadership roles

### Phase 2. Appoint

- Confirm leadership
- Resolve critical talent decisions
- Assign ownership

### Phase 3. Transition

- Move teams
- Transfer responsibilities
- Change reporting
- Update systems

### Phase 4. Stabilize

- Resolve interface failures
- Monitor workload
- Adjust spans
- Reinforce decisions

### Phase 5. Optimize

- Remove remaining duplication
- Improve processes
- Review economics

Do not announce a reorganization without an operating transition plan.

# 30. Know When Not to Reorganize

Do not redesign structure when the primary problem is:

- Poor strategy
- Weak leadership
- Insufficient capability
- Broken processes
- Poor data
- Weak performance management
- Unclear priorities
- Lack of accountability
- Temporary underperformance
- A single failed initiative

Ask:

**What evidence indicates that structure is causing the problem?**

If the answer is weak, diagnose further.

Reorganizations consume attention, create uncertainty, and introduce execution risk.

Use them when structural change is actually required.

# Executive Standard

At any point, leadership should be able to answer:

**Does our organization reflect our strategy?**

**Are critical business outcomes clearly owned?**

**Does authority sit with accountability?**

**Are decisions made at the appropriate level?**

**Where does organizational friction slow execution?**

**Are critical interfaces designed?**

**Do we have the capabilities the strategy requires?**

**Are management layers creating value?**

**Are spans appropriate for the work?**

**Do senior leaders have realistic capacity?**

**What should be centralized?**

**What should remain local?**

**Can the organization scale without proportional complexity?**

**What structural changes are actually required?**

**How will we know the new model works?**

If leadership cannot answer these questions, changing the organization chart is premature.

---

# Operating Principle

> **Start with strategy.**
>
> **Understand the work.**
>
> **Define the outcomes.**
>
> **Place accountability.**
>
> **Align authority.**
>
> **Design the interfaces.**
>
> **Build the capabilities.**
>
> **Test the economics.**
>
> **Protect execution during transition.**
>
> **Measure whether the organization performs better.**

The purpose of organizational design is not to create a cleaner organization chart.

It is to build an organization capable of executing the strategy with clear accountability, appropriate authority, strong economics, and less organizational friction.
